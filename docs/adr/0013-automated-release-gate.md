# Автоматический гейт перед публикацией релиза

Публикация образов допускается только после зелёного автоматического гейта, а не после одной успешной сборки. Гейт — `scripts/release-gate.sh`: единый набор именованных этапов, каждый со своей диагностикой в `deploy/gate-artifacts/<этап>.log`; провал печатает этап, хвост журнала и путь к полному журналу, сводка — `summary.txt`.

Этапы: `shell` (`bash -n` + shellcheck), `deploy` (deploy-suite конфигурации), `infra` (`docker compose config` dev/prod, `caddy validate`, `otel-collector validate`), `backend` (быстрые тесты), `postgres` (критические гарантии PostgreSQL), `migrations` (drift-guard EF Core), `frontend` (Vitest state-тесты и чистая сборка по lockfile), `deps` (findings по уязвимым зависимостям и образам), `browser` (сквозной smoke в браузере, opt-in). На хосте нужен только Docker: .NET SDK, Node и Postgres не устанавливаются — этапы идут в контейнерах, поэтому критические проверки воспроизводятся без SDK.

Обычная проверка не требует production-секретов, не деплоит сервер и не публикует образы. `deploy/build-push.sh` вызывает гейт перед сборкой; на `--publish` дополнительно прогоняется browser smoke, и только затем образы уходят в registry. CI (GitHub Actions, `.github/workflows/release-gate.yml`) согласован с локальным запуском: job гейта выполняется на push/PR, job публикации зависит от него (`needs`) и запускается только по тегу.

Гейт проверяемый: намеренная SQL-ошибка проваливает `postgres`, гонка во frontend-тесте — `frontend`, неверная Compose/Caddy/Collector-конфигурация — `infra`; тесты используют управляемые ответы и изолированные каталоги. Browser smoke управляемо берёт код подтверждения из журнала backend (без случайных пауз), а `trap` очищает контейнеры, volumes и временные файлы. Анализ зависимостей только сообщает конкретные findings и сохраняет их; политика обработки (обновить или обоснованно принять, блокирующий режим через `GATE_AUDIT_ENFORCE=1`) зафиксирована в `deploy/README.md`. Диагностика не печатает секреты и содержимое окружения.

# Деплой на собственный VPS в Docker Compose

Приложение разворачивается на собственном VPS/VDS (Ubuntu 24.04 LTS) через Docker Compose. Caddy — единственный вход (80/443): `/api/*` и `/health` идут на backend, `/` — на frontend (nginx, статика). Postgres — свой контейнер без публикации порта, пароль из env. Образы backend и frontend собираются локально `deploy/build-push.sh` и публикуются в Docker Hub тегами `:<git-sha>` + `:latest`; деплой и откат — `deploy/deploy.sh <sha>`. Бэкапы (`pg_dump` + фото) уходят через `rclone` в объектное хранилище, логи — через OpenTelemetry Collector в консоль и файл.

Изначально планировался PaaS Amvera (managed PostgreSQL, деплой по webhook); от него отказались в пользу собственного сервера. Это даёт полный контроль над данными и расходами, провайдер-агностичность и отсутствие привязки к платформе, ценой того, что обновления, TLS, бэкапы и наблюдаемость лежат на нас. Managed-база заменена своим Postgres — дешевле, но требует собственных бэкапов и регулярной проверки восстановления.

Следствия: конвенция деплоя — в `deploy/README.md`; на сервере живут `docker-compose.prod.yml`, `Caddyfile`, `otel-collector.yaml`, серверные скрипты с общей библиотекой в `deploy/` и `server.conf`; домен и HTTPS подключаются установкой `DOMAIN`. Начиная с тикета 36, конфигурация — literal-данные `KEY=value`, без shell source: локальный `deploy/local.conf` отделён от серверных секретов. Серверный Compose запускается через общую библиотеку/`deploy/compose.sh`, с отключённым автоматическим чтением `.env`; окружение имеет приоритет над файлом, включая явно пустые значения.

Начиная с тикета 49, SMTP-соединение обязательно защищено: `SMTP_SECURITY=starttls` (по умолчанию, порт 587) требует STARTTLS, `ssl` включает неявный TLS (порт 465); даунгрейда «когда доступно» и отключения проверки сертификата нет. Несовместимые host/port/TLS и неполные поля отклоняются на старте без секретов; сбой ограничен `SMTP_TIMEOUT_SECONDS` и не считается доставкой. Полное письмо (код и HTML) в журнал пишется только явно (`EMAIL_TRANSPORT=log`) и только в `lab`; в production это запрещено, а надёжная очередь — задача тикета 50.

Начиная с тикета 44, публичный запуск защищён на старте backend: режим `DEPLOYMENT_MODE=production` (по умолчанию) требует HTTPS-адрес `PUBLIC_BASE_URL`, настроенную почту и случайные не-шаблонные секреты, а `lab` — явный лабораторный режим с HTTP и письмами в лог. Проверка не печатает значения секретов и отклоняет известные dev/placeholder-шаблоны, а не только короткий JWT-секрет. Backend в образе работает от непривилегированного пользователя с подготовленным `PHOTOS_DIR`; prod-Compose минимизирует capabilities (`cap_drop: ALL` где совместимо, `NET_BIND_SERVICE` только Caddy) и включает `no-new-privileges`, сохраняя исходящий SMTP. Ресурсный бюджет — измеряемое требование к VPS (≥2 vCPU, ≥2 ГБ RAM + swap, ≥40 ГБ диска), лимиты памяти/CPU и проверки свободного места для backup/drill; окно backup (02:30–02:40) не пересекается с плановым reboot (04:30). Dev-порты привязаны к `127.0.0.1`, prod публикует только 80/443.

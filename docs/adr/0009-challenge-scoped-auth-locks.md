# Блокировка кода привязана к операции, а не навязывается анонимно

Исчерпание неверных попыток по одноразовому коду закрывает **конкретный код** (`AuthCode.Used`), а счётчик попыток живёт на самом коде (`AuthCode.Attempts`), не на пользователе. Поведение двух операций намеренно разное. Подтверждение почты выполняется залогиненным пользователем, и после 5 неверных попыток оно, как и прежде, блокирует операцию на `User.LockedUntil = now + 3 дня` (сбрасывается админ-разблокировкой). Сброс пароля — анонимная операция: посторонний, знающий email, не должен мочь запросами без действующего кода навязать длительную блокировку восстановления. Поэтому превышение попыток по reset закрывает только текущий challenge, аккаунт не блокируется, а после штатного cooldown пользователь получает новый код; запросы вообще без действующего кода (отсутствующего, истёкшего, уже потреблённого) не засчитываются и ничего не блокируют.

Атомарность обеспечивает общий `AuthCodeLifecycle`: выдача, cooldown, выбор единственного действующего challenge и операция «потребить код + записать новый хэш пароля + инкрементировать `TokenVersion`» выполняются в одной транзакции с блокировкой строки пользователя. Так два reset одним кодом дают ровно одну успешную смену, а конкурентные неверные попытки не теряются.

Альтернатива — оставить единую блокировку на пользователе для обеих операций — отвергнута: она превращала анонимный ввод кода в орудие отказа в обслуживании (3 дня недоступного восстановления по одному email) и связывала между собой независимые операции. Отказ от аккаунт-локировки для reset не ослабляет перебор: шестизначный код живёт 1 час и закрывается после 5 промахов, а после закрытия нужен новый код.

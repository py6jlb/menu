# Схема БД ведётся EF Core миграциями

`EnsureCreated` заменён на EF Core миграции. При старте backend применяет `MigrateAsync` (только для relational-провайдера), без флагов окружения и ретраев: ошибка миграции роняет процесс (fail-fast), а готовность Postgres к моменту старта гарантирует `depends_on: service_healthy` в compose. Одна `Initial`-миграция фиксирует текущую модель; локальный манифест `.config/dotnet-tools.json` прибивает `dotnet-ef`, а `deploy/build-push.sh` падает на `has-pending-model-changes`, если модель и миграции разошлись.

Миграции пишутся только вперёд: down-миграции не поддерживаются, и откат версии приложения не откатывает схему. EF при генерации миграции создаёт метод `Down()`, но это лишь шаблон scaffolding: репозиторий не использует down-миграции и не считает их поддерживаемым путём отката. Откат — восстановление БД из бэкапа (см. ADR-0006) вместе с деплоем прежнего образа: сначала данные, затем код.

Откат разделён на два явных пути (тикет 41, `deploy/rollback.sh`). При совместимой схеме это **code-only**: меняется только образ, схема остаётся новой — простая замена образа не подаётся как возврат старой схемы. При несовместимом изменении схемы релиз объявляется `--schema-change`: перед переключением снимается свежая согласованная recovery-точка (complete-набор), привязанная к обновлению, а откат идёт **recovery** — записи останавливаются, данные и фото восстанавливаются из набора, затем ставится прежний release. Down-миграции не становятся неявным способом отката; параллельные деплои/откаты сериализуются lock-файлом, а прерванная операция оставляет диагностируемое состояние current/previous release.

Тесты остаются на EF InMemory: гард `IsRelational()` пропускает миграции, а основной suite не поднимает реальную Postgres. Это осознанное исключение для быстрых проверок поведения приложения; от рассинхрона модели и миграций дополнительно страхует drift-guard в сборке.

Критические гарантии PostgreSQL проверяются отдельным узким suite, а не размазыванием реальной БД по всем тестам. Suite включается только при заданной строке подключения `MENU_PLANNER_TEST_POSTGRES` и запускается `scripts/test-postgres.sh`: скрипт поднимает одноразовый `postgres:16` (та же основная версия, что в проде) в изолированной Docker-сети без публикации порта и без volume, создаёт на каждый тест уникальную БД и удаляет её после, а сам тест исполняется в контейнере SDK — на хосте .NET SDK не нужен. Без переменной окружения PostgreSQL-классы пропускаются, поэтому быстрый suite остаётся прежним. Для последующих тикетов доступен `AsyncBarrier` — детерминированная точка пересечения двух независимых контекстов/запросов без случайных задержек. Startup migrate, fail-fast и forward-only остаются в силе: одна проверка прогоняет штатный старт приложения на пустой БД и повторный запуск без потери данных.

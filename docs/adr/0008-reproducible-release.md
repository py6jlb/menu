# Воспроизводимый и однозначно идентифицируемый релиз

Релиз — это коммит git и собранные из него образы. `deploy/build-push.sh` собирает образы с тегом `:<git-sha>` и пишет manifest `deploy/release/<tag>.json`: commit, `builtAt`, дайджесты backend/frontend, хэши файлов выпускаемого среза. Сборка отклоняет незакоммиченные изменения, поэтому под идентификатором чистого commit нельзя опубликовать чужой код. Публикация образов выполняется только явным `--publish`; `latest` остаётся вспомогательным указателем и не заменяет закреплённую версию.

`deploy/deploy.sh <sha>` требует чистый checkout ровно на этом коммите и доставляет конфигурации выпускаемого среза (при наличии manifest сверяет их хэши): повторный деплой старого релиза не подмешивает новые локальные файлы. Серверный `remote-deploy.sh` после `pull` и проверки `/health` сохраняет выбранный тег в `/opt/menu/current-release` и manifest с дайджестами запущенных образов в `/opt/menu/release.json`. `config_server` читает `current-release` ниже окружения и `server.conf`, поэтому повторный штатный Compose использует тот же тег без временного экспорта в SSH-сессии. `deploy/smoke.sh` подтверждает идентичность manifest и живой путь.

Следствия: frontend собирается в поддерживаемой LTS Node (`frontend/.nvmrc`, `engines`) только по `frontend/package-lock.json` (`npm ci`), чистая установка не меняет lockfile; базовые образы закреплены контролируемыми тегами с документированным порядком обновления; отсутствующий статический asset под `/assets/` отдаёт 404, а SPA-маршруты по-прежнему падают на `index.html`. Откат — деплой предыдущего sha вместе с его срезом; down-миграции по-прежнему не поддерживаются, восстановление схемы — из бэкапа (ADR-0006, ADR-0007).

# Лимиты аутентификации — в памяти одной реплики, с доверенным прокси и ограниченными ключами

Вход, регистрация, сброс пароля и операции с кодами ограничены по частоте локальным лимитером фиксированных окон (`FixedWindowRateLimiter`), который живёт в памяти процесса backend. Это осознанный выбор для одной реплики: внешний store (Redis) не требуется, потому что у нас один экземпляр backend. Лимитер потокобезопасен, число ключей ограничено (`AUTH_RATE_LIMIT_MAX_TRACKED_KEYS`, по умолчанию 10000), устаревшие окна удаляются пачками, а при переполнении новыми неистёкшими окнами новые ключи отклоняются (fail-closed для новых ключей), уже отслеживаемые окна не вытесняются. Так поток уникальных email или адресов под перебором не растёт в памяти неограниченно.

Проверка идёт в порядке «сначала IP, затем операция/email/пользователь». Если IP уже исчерпан, ключ операции не создаётся вовсе — иначе атакующий с ограниченного адреса на каждый запрос порождал бы новый email-ключ. Лимит на операцию/пользователя нужен, потому что IP-адрес общий для семьи за NAT: без него один шумный пользователь блокировал бы всех. Отказ единообразен: `429` с заголовком `Retry-After`; UI ограничиваемых операций показывает срок и снимает pending.

Клиентский IP берётся только из `HttpContext.Connection.RemoteIpAddress` после `UseForwardedHeaders`, и forwarded-заголовки принимаются лишь от доверенных `TRUSTED_PROXY_ADDRESSES`/`TRUSTED_PROXY_NETWORKS`. Если список пуст, middleware не подключается: в ASP.NET Core пустой известный список прокси трактуется как «доверять всем», поэтому «доверять никому» достигается отсутствием middleware, а не пустыми списками. В prod доверен край Caddy (статический адрес в сети `edge`), backend не публикует порт; в dev — nginx-вход. Сырой `X-Forwarded-For` не считается доверенным.

Альтернативы. Сразу поднять Redis ради распределённых счётчиков — лишняя инфраструктура и точка отказа для одного экземпляра, поэтому отложено. Доверять сырому `X-Forwarded-For` — позволяет подделать IP и обойти лимиты. Хранить ключи без границы — неограниченная память под перебором. Вытеснять самый старый ключ при переполнении — атакующий вытеснял бы собственный IP-ключ и обходил лимит, поэтому выбран отказ новым ключам.

Последствие: при масштабировании на несколько реплик локальный лимитер перестаёт быть общим — счётчики реплик независимы, и суммарный лимит умножается на их число. Переход к общему хранилищу (например, Redis) — отдельное ограничение и отдельная задача; текущая конфигурация намеренно обходится без него.

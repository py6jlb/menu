# 61: Подбор доступных блюд с актуальными фильтрами и поиском

**What to build:** Пользователь выбирает доступное блюдо по текущим фильтрам и поиску: сломанный источник не предлагается как пригодный, отозванная ссылка остаётся доступной с пояснением, выбранное имя и состояние не теряются при изменении выдачи.

**Blocked by:** 60 — Единое актуальное чтение рецепта для списка и деталей.

**Status:** resolved (commits c07bf1c, 6555413)

- [x] Подбор использует единое чтение актуального контента; broken исключён из доступной выдачи и не может быть подтверждён как доступное блюдо.
- [x] Warning остаётся доступным по ADR; результат передаёт достаточно metadata состояния/происхождения и не маскирует внешний рецепт под обычный.
- [x] Выбор хранится отдельно от текущей выдачи; исчезновение выбранного рецепта из нового фильтра не создаёт запись с пустым именем или неявно другим состоянием.
- [x] Изменение только порций сохраняет актуальное имя/state записи; перед подтверждением недоступного выбора пользователь получает объяснение.
- [x] Черновые и применённые фильтры согласованы; «Сбросить» действительно получает выдачу без фильтров, поздний ответ не заменяет более новый.
- [x] Поиск имени выполняется на сервере до ограничения результата, с ограниченной выдачей и стабильным порядком; рецепт вне первой сотни находится поиском.
- [x] Ошибка подбора показана рядом с операцией, pending завершается, существующий план/выбор не очищаются.
- [x] Проверены broken/warning, фильтрация выбранного рецепта, сброс, обратные ответы, более 100 рецептов и сохранение metadata при изменении порций.
- [x] Чистые правила жёстких фильтров и мягких предпочтений сохранены; расчёт повторяемости добавляется отдельным тикетом.

## Evidence

- **Единое чтение.** `RecipeReader.ReadMatchCandidatesAsync` (`backend/src/MenuPlanner.Api/Recipes/RecipeReader.cs`) отдаёт `RecipeMatchCandidate`: живой контент внешнего рецепта спроецирован на источник (`ExternalRecipeContentResolver.Resolve`), локальные id/принадлежность сохранены, состояние и подпись семьи-источника разрешены модулем. Сломанный источник (`Broken`) пропускается — его нельзя подтвердить как доступное блюдо. Оркестрация состояния/кэша имени/семей вынесена в общий `ResolveExternalContextAsync`, который используют обе проекции чтения (список и подбор), поэтому правила не расходятся.
- **Поиск до лимита.** `RecipeMatcher.Apply(source, filters, preferences, search)` применяет поиск по имени (trim, регистронезависимо) внутри `Where` до `Take(MaxResults)`; порядок `score → имя → id` сохранён. `RecipeMatchRequest.Search`, endpoint `MatchAsync` больше не знает про `ExternalRecipeSourceLoader`.
- **Metadata в ответе.** `RecipeMatchItemDto` дополнен `IsExternal`, `SourceFamilyName`, `State` (по `ExternalRecipeStateRules.Code`), поэтому внешний рецепт не маскируется под обычный; warning приходит с состоянием и происхождением.
- **Frontend.** `useRecipePicker` (`frontend/src/composables/useRecipePicker.js`): выбор (`selection`) хранится отдельно от выдачи; присутствующий в свежей выдаче выбор синхронизируется актуальными именем/state, исчезнувший — сохраняет прежние; `draftFilters` отделены от `appliedFilters`, «Сбросить» перезапрашивает пустые фильтры; поиск уходит на сервер (debounce в `PlanView`); номер запроса гасит поздний ответ; ошибка сохраняет выдачу, выбор и завершает pending. `confirm()` не подтверждает broken и объясняет через `selectionWarning` (ADR-0005: «убрать или заменить»). `PlanView.vue` показывает состояние/происхождение в списке и сохранённый выбор вне выдачи.

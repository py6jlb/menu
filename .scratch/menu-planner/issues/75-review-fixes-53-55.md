# 75: Исправления двухосевого ревью тикетов 53 и 55

**What to build:** Устранить находки ревью по двум осям (Standards и Spec) для диффа `1ecc2f2...HEAD`: убрать `static`-хелперы с `AppDbContext`, дедуплицировать чтение ревизии и путь чтения плана, провести операции с фото через ревизионный сервис, починить UI-восстановление после конфликтов и сравнение плана, обновить контракт API и терминологию.

**Blocked by:** None (can start immediately)

**Status:** in-progress

## Standards

- [ ] `README.md` описывает `revision`/`409`/`400` для `PUT`/`DELETE`/`copy`/фото рецепта.
- [ ] Убраны `static`-методы, принимающие `AppDbContext` (`PlanEndpoints.ConflictAsync`, `RecipeEndpoints.ConflictAsync`, `RevisionProblem`).
- [ ] Запрос текущей ревизии рецепта вынесен в один scoped-сервис `RecipeRevisionReader`.
- [ ] Путь чтения плана вынесен в scoped `WeekPlanReader`; GET/успех PUT/конфликт используют один проектор.
- [ ] Операции фото идут через `RecipeMutationService` (одна защита ревизии).
- [ ] `RecipeTarget` группирует `(Id, FamilyId)`; `revision` осознанно остаётся `int` — это токен конкурентности EF.
- [ ] Обновление кэша имени внешнего рецепта — scoped `ExternalRecipeNameCache` с одной безопасной попыткой.

## Spec

- [ ] `RecipeDetailView` показывает конфликт ревизии при удалении/локальном удалении/копировании и предлагает загрузить актуальную версию.
- [ ] `RecipeFormView` при сбое фото после успешного сохранения текста показывает частичный результат и позволяет повторить только действие с фото.
- [ ] `PlanView` при конфликте показывает построчное сравнение серверной и локальной версий, а не только число записей.
- [ ] `DELETE /photo` без фото — no-op без роста ревизии.
- [ ] Миграция ревизии недели проставляет существующим планам `Revision = 1`, не смешивая с sentinel `0`.
- [ ] Кэш имени обновляется при каждом чтении (с повтором при гонке), а не молча пропускается.

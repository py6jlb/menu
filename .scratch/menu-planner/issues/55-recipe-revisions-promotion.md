# 55: Конкурентное редактирование и однократный промоушен в копию

**What to build:** Участник семьи редактирует рецепт без молчаливой перезаписи более новой версии; внешний рецепт становится копией только один раз, даже при одновременном нажатии двумя участниками, сохраняя свой идентификатор и связи с планом.

**Blocked by:** 37 — Проверка критических гарантий на PostgreSQL; 54 — Черновик рецепта с правильной идентичностью и защитой от потери.

**Status:** resolved (ticket/55-recipe-revisions-promotion; commit 98b5379)

- [x] Рецепт имеет проверяемую ревизию; чтение и редактирование передают ожидаемую версию, изменение атомарно проверяет её.
- [x] Устаревшее сохранение даёт согласованный конфликт; UI сохраняет локальные поля и объясняет необходимость получить/сравнить актуальную версию без автоматического overwrite.
- [x] Переход внешний рецепт → собственная копия защищён до вставки зависимого контента и файловых эффектов, а не только повторной проверкой после копирования.
- [x] Два промоушена создают один набор шагов и ингредиентов; повтор возвращает предсказуемый результат/конфликт, не повторяет копирование фото.
- [x] Промоушен сохраняет ID и записи плана, копирует актуальный контент и фото, ставит происхождение; warning можно сохранить, broken — нельзя.
- [x] Изменения фото/удаление и пересекающиеся операции учитывают ревизию рецепта; последующие тикеты могут использовать ту же защиту lifecycle.
- [x] Существующие рецепты и внешние ссылки сохранены миграцией; обычное редактирование внешнего и транзитивный sharing остаются запрещены.
- [x] Проверены конкурирующие PUT, двойной copy, copy/удаление и ошибка после начала операции на PostgreSQL; frontend-тест подтверждает сохранность черновика при конфликте.

## Evidence

- `Recipe.Revision` (`int`, стартует с 1) объявлена токеном конкурентности EF Core (`IsConcurrencyToken`, default 1); миграция `20261006091121_AddRecipeRevision` добавляет колонку с `defaultValue: 1`, сохраняя существующие рецепты и внешние ссылки.
- Чистое правило `Recipes/RecipeRevisionRules.cs` (`Initial`, `IsCurrent`, `Next`, сообщения конфликта/отсутствия версии); валидация и перенос запроса вынесены в статический `Recipes/RecipeValidation.cs`.
- БД-сервисы по конвенции CONTEXT.md: `RecipeMutationService` (правка/удаление/локальное удаление собственных и внешних рецептов с атомарной проверкой ревизии, ловит `DbUpdateConcurrencyException`) и `ExternalRecipePromotionService` (условный выкуп строки `ExecuteUpdateAsync` по ревизии и `SourceRecipeId` в транзакции **до** копирования контента и фото; при ошибке после начала — откат и удаление осиротевшего файла). Оба зарегистрированы scoped в `Program.cs`.
- `RecipeEndpoints`: `PUT` принимает `RecipeRequest.Revision`, `DELETE`/`DELETE .../external`/`POST .../copy`/`DELETE .../photo` — query `revision`, `PUT .../photo` — query `revision`. Устаревшее — `409 RecipeConflictDto` (с актуальной ревизией), отсутствие — `400`. Внешний рецепт до промоушена по-прежнему read-only (`403`), транзитивный шаринг запрещён. Кэш имени источника (`GET`/list) не роняет чтение при гонке правок.
- Frontend: `useRecipeDraft` отслеживает ревизию, передаёт её в теле сохранения, на `409` сохраняет черновик и выставляет `conflictMessage`/`conflictRevision`; `RecipeFormView` показывает сообщение и кнопку «Загрузить актуальную версию» (явное подтверждение, без авто-overwrite); `RecipeDetailView` и `RecipeFormView` передают ревизию в удаление/промоушен/фото (`api/recipes.js`).
- Тесты: `RecipeRevisionFlowTests` (чтение, stale/absent PUT, delete, photo, copy — 7); `Postgres/PostgresRecipeRevisionTests` (конкурирующие PUT, stale PUT, двойной промоушен с одним фото и одним набором контента, stale local remove, промоушен+удаление, откат при ошибке после начала — 6); `frontend/src/composables/useRecipeDraft.test.js` — 4 теста на передачу/приём ревизии, сохранность черновика при конфликте и сброс состояния.

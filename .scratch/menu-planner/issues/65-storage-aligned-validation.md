# 65: Предсказуемая валидация и точное сохранение данных

**What to build:** Пользователь получает понятную ошибку у поля вместо 500 или скрытого округления: принятое количество ингредиента и другие значения сохраняются именно в допустимом виде, а некорректные коллекции безопасно отклоняются.

**Blocked by:** 37 — Проверка критических гарантий на PostgreSQL.

**Status:** ready-for-agent

- [ ] Для количества сохранена точность до сотых без молчаливого округления: положительное значение с ненулевыми знаками дальше второго десятичного отклоняется, лишние хвостовые нули не считаются большей точностью.
- [ ] Допустимый диапазон согласован с текущим decimal-хранилищем; ноль, отрицательное значение и переполнение отклонены до записи.
- [ ] Названия, описание, шаги, примечания, email и имя семьи проверяются относительно реальных ограничений хранения; нормализация не меняет принятый смысл.
- [ ] Null-элементы в ингредиентах, шагах, тегах, сезонах, диетах и записях плана, malformed payload и чрезмерные коллекции дают контролируемый отказ, не исключение обращения к null.
- [ ] Ошибки ввода имеют согласованную внешнюю форму с машинным кодом, русским объяснением и привязкой к полю; клиент сохраняет черновик и показывает причину.
- [ ] Конфликт, недоступность и неожиданная внутренняя ошибка не маскируются под validation; неожиданный ответ не раскрывает stack trace/SQL/секреты и допускает корреляцию запроса.
- [ ] После принятия значения create/update/read возвращают одинаковое число; расчёт покупок сохраняет существующую decimal-арифметику без нового округления.
- [ ] На PostgreSQL проверены малые дроби, хвостовые нули, границы диапазона, длинные строки и round-trip; HTTP/frontend-проверки покрывают null-коллекции и отображение field errors.

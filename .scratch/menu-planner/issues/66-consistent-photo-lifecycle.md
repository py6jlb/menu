# 66: Согласованный жизненный цикл файлов фото

**What to build:** Загрузка, замена, удаление и промоушен фото не оставляют БД и файловое хранилище в противоречии при сбое; пользователь получает результат фактической операции, а безопасная уборка удаляет только действительно бесхозные файлы.

**Blocked by:** 55 — Конкурентное редактирование и однократный промоушен в копию.

**Status:** resolved (ticket/66-consistent-photo-lifecycle; commit 31cb757)

- [x] Жизненный цикл фото сосредоточен в предметном модуле, использует ревизию рецепта и явно согласует файл с DB-commit.
- [x] Новый файл удаляется компенсацией при неуспехе записи БД; если компенсация сама неуспешна, файл остаётся диагностируемым кандидатом для уборки.
- [x] Старый файл удаляется после commit повторяемой операцией; ошибка cleanup не возвращает ложный общий неуспех уже завершённого изменения рецепта.
- [x] Параллельные замены, загрузка/удаление рецепта и copy/смена фото источника не удаляют актуальный файл и не создают незамеченных постоянных сирот.
- [x] Уборка проверяет ссылки и безопасный возраст файлов, не трогает незавершённую загрузку/копирование или файлы, нужные текущему backup.
- [x] Согласована сохранность старых файлов с backup-набором: новые правила не нарушают точку восстановления при одновременной замене фото.
- [x] Существующая политика публичного URL сохранена: отзыв ссылки не объявляется отзывом ранее полученного URL фото; изменение приватности не входит в этот тикет.
- [x] Проверены ошибка DB после записи файла, ошибка удаления после commit, конкурентные замены и промоушен; инспекция после cleanup подтверждает отсутствие потери актуальных фото.

## Evidence

- Предметный модуль жизненного цикла: `Recipes/Photos/PhotoLifecycle.cs` — `ReplaceAsync`/`CopyFromAsync` пишут новый файл, выполняют изменение БД через `PhotoCommit<T>` (`Committed=false` = конфликт/отказ) и сами согласуют результат: подтверждённый commit → `Retire(previous)`, отказ → `Discard(staged)`. Ошибки `Retire`/`Discard` логируются и не возвращают ложный общий неуспех (файл остаётся кандидатом `PhotoGarbageCollector`). Порядок «новый до commit, старый после» гарантирует, что актуальная ссылка никогда не ведёт на удалённый файл.
- Ревизия: `RecipeMutationService.UploadPhotoAsync`/`DeletePhotoAsync`/`DeleteTrackedAsync` и `ExternalRecipePromotionService.PromoteRelationalAsync`/`PromoteTrackedAsync` передают ожидаемую ревизию и остаются единственной точкой проверки (конвенция тикета 75); файловые эффекты идут через `PhotoLifecycle`. В промоушене с явной транзакцией `CommitAsync` отделён от подготовки: при неоднозначном сбое commit ни новый, ни предыдущий файл не удаляются.
- Порт хранилища: `IPhotoStore` (`Save`/`Copy`/`Delete`/`Resolve`/`List`), singleton-реализация `PhotoStorage`. `SaveAsync` убирает частичный файл при сбое записи; `CopyAsync` терпим к конкурентно исчезнувшему источнику (возвращает null, не роняя промоушен).
- Безопасная уборка: `PhotoGarbageCollector.CollectAsync(minimumAge)` удаляет только управляемые имена (`PhotoFileNames`, чистый статик-правило: `{recipeId:N}-{guid:N}.{ext}`), не упомянутые ни одним `Recipe.PhotoPath` и старше безопасного возраста; ошибки удаления считаются и не роняют проход. `PhotoCleanupOptions` (enabled/интервал/возраст, дефолт 24 ч) и hosted `PhotoCleanupWorker`; в тестах `PHOTO_CLEANUP_ENABLED=false`.
- Backup: уборка идёт в backend, который `backup.sh` останавливает на время снятия набора, поэтому файлы набора не трогаются; замена фото сохраняет старый файл до commit. Зафиксировано в `deploy/README.md` и `CONTEXT.md` («Жизненный цикл фото», раздел «Разделение кода»).
- Публичный URL `/api/photos/{file}` не изменён (вне группы авторизации), политика отзыва ссылки не затронута.
- Тесты: `PhotoLifecycleServiceTests` (7) — отказ записи БД убирает новый файл, сбой удаления старого после commit не роняет операцию, сбой компенсации не бросает и оставляет файл уборке, отказ промоушена убирает копию; `PhotoGarbageCollectorTests` (2); `PhotoFileNamesTests` (8); `PhotoStorageTests` (2); `PostgresPhotoLifecycleTests` (2) — конкурирующие замены, гонка замена/удаление рецепта, уборка после промоушена сохраняет файл источника и копию; `RecipePhotoTests`/`RecipeRevisionFlowTests`/`ExternalRecipePromotionTests` — регрессия HTTP-потока.
- Команды: `dotnet test` — 499 passed / 58 skipped (Postgres без env); `scripts/test-postgres.sh` — 61 passed; `npm run build` — успешно.

# 67: Проверка настоящего изображения при загрузке

**What to build:** Пользователь загружает действительное поддерживаемое изображение; поддельный MIME, повреждённый файл и чрезмерные размеры отклоняются понятно, не заменяя прежнее фото и не исчерпывая ресурсы обработки.

**Blocked by:** None (can start immediately)

**Status:** resolved (ticket/67-real-image-validation; commits 92eb2c1, 0e80c3c)

- [x] Проверяются фактический формат и декодирование, а не только присланный ContentType/расширение; содержимое, не являющееся изображением, отклоняется.
- [x] Сохранены поддерживаемые пользовательские форматы либо явно описана совместимая обработка; тип выдачи соответствует фактически сохранённому содержимому.
- [x] Ограничены размер входного файла, размеры/пиксели и ресурсы декодирования; очень большое изображение малого файлового размера не обходит защиту.
- [x] Если применяется перекодирование/удаление metadata, поведение явно задано и не портит поддержку согласованных форматов, ориентацию и отображение.
- [x] Отказ не меняет ссылку БД и не удаляет предыдущее фото; частичные временные файлы очищаются.
- [x] UI сообщает ограничение до загрузки, отображает окончательный серверный отказ и допускает другой выбор без потери рецепта.
- [x] Тестовые фото — реальные валидные изображения; проверены текст с image MIME, повреждённое изображение, mismatch формата, чрезмерные dimensions и успешная загрузка/выдача.

## Evidence

- **Формат и декодирование по содержимому.** Предметный stateless-модуль `Recipes/RecipeImageValidator.cs`: `Image.DetectFormat` определяет формат по сигнатуре (не по `ContentType`/имени), `Image.Identify` читает размеры из заголовка, затем `Image.Load(DecoderOptions{MaxFrames=1})` декодирует первый кадр. Любой `ImageFormatException`/`NotSupportedException` → русская ошибка `NotImageError`. `UploadPhotoAsync` (`RecipeEndpoints.cs`) читает файл в память (≤5 МБ), проверяет валидатором и передаёт **определённое по содержимому** расширение в `RecipeMutationService.UploadPhotoAsync`. Прежняя проверка `ContentType` удалена: поддельный MIME и mismatch формата обрабатываются по фактическим байтам.
- **Тип выдачи = сохранённому содержимому.** Хранится расширение фактического формата (`.jpg`/`.png`/`.webp`/`.gif`), `/api/photos/{file}` отдаёт Content-Type по расширению, поэтому ответный тип совпадает с байтами, даже если клиент объявил `image/jpeg` для PNG.
- **Лимиты и ресурсы.** `RecipeCatalog.PhotoMaxBytes` (5 МБ, проверяется до чтения), `PhotoMaxDimension` (8000 по стороне), `PhotoMaxPixels` (25 Мпикс). Размеры проверяются по заголовку **до** декодирования, поэтому PNG-«бомба» 5001×5001 малого файлового размера отклоняется без аллокации пикселей; `MaxFrames=1` ограничивает расходы на многокадровых GIF.
- **Без перекодирования.** Оригинальные байты сохраняются как есть: анимация GIF, метаданные и ориентация EXIF не меняются (тест `UploadPhoto_AnimatedGif_StoresOriginalBytesUnchanged` сравнивает выданные байты с исходными). Комментарий валидатора явно фиксирует это поведение; re-encode/metadata stripping не применяется.
- **Отказ безопасен.** Валидация идёт до `UploadPhotoAsync`, поэтому БД-ссылка и ревизия не меняются, предыдущий файл не удаляется (тест `UploadPhoto_InvalidImage_KeepsPreviousPhotoAndRevision`). Частичная запись устраняется компенсацией `PhotoStorage.SaveAsync` из тикета 66; отдельный тест `PhotoStorageTests.SaveAsync_WhenStreamFails_LeavesNoPartialFiles` подтверждает отсутствие файла после обрыва потока. В `RecipePhotoTests` после отказа проверяется отсутствие `*.tmp`.
- **UI.** `constants/recipe.js`: `PHOTO_MAX_DIMENSION`/`PHOTO_MAX_PIXELS`/`PHOTO_DIMENSIONS_LABEL` и чистая `validatePhotoDimensions(width, height)`; `RecipeFormView` до отправки декодирует выбранный файл (`createImageBitmap` с fallback на `Image`) и отклоняет повреждённый или чрезмерный файл понятным сообщением, а также печатает лимиты в подсказке. Серверный отказ отображается в `photoError` (из тикета 56), черновик текста сохраняется; `useRecipeDraft.reconcilePendingPhoto` перед повтором фото применяет **новый** выбор пользователя, поэтому после отказа можно выбрать другой файл и отправить его (тесты `useRecipeDraft.test.js`).
- **Тестовые изображения.** `TestImages` генерирует реальные PNG/JPEG/GIF/WebP. `RecipePhotoTests` покрывает: успешную загрузку/выдачу всех четырёх форматов, текст с `image/png`, повреждённый (обрезанный) PNG, mismatch `ContentType`, чрезмерные сторону/пиксели (валидный PNG-заголовок с корректным CRC, без данных) и анимационный GIF. Прежние HTTP-тесты с заглушками (`SharedRecipeFlowTests`, `ExternalRecipeImportTests`, `ExternalRecipePromotionTests`, `RecipeRevisionFlowTests`) переведены на реальные изображения.
- **Зависимость.** `SixLabors.ImageSharp 3.1.12` (чистая managed-библиотека, поддержка JPEG/PNG/WebP/GIF, лицензия Six Labors Split — бесплатна для этого проекта). Версия 4.x отклонена: её build-target требует лицензионный ключ и ломает `dotnet publish -c Release`; 3.1.12 — последний патч ветки 3.x без обязательного ключа, `dotnet build -c Release` проходит.
- **Проверки.** `dotnet test` — Failed: 0, Passed: 542, Skipped: 59 (Postgres без env); `dotnet build -c Release` — успешно; frontend `npm test` — 189 passed, `npm run build` — успешно.
- **Ревью.** Двухосевое ревью: устранены дублирование лимитов в тексте ошибки (собирается из констант), неиспользуемые поля `ValidatedPhoto` (сигнатура сужена до расширения), неиспользуемые константы фронта (задействованы в проверке размеров), узкий набор исключений (базовый `ImageFormatException`), дублирование сброса фото-результата (`clearPhotoResult`).

# 73: Автоматический гейт перед публикацией релиза

**What to build:** Разработчик получает автоматический проверяемый результат готовности релиза: публикация допускается только после проверок кода, реальной БД, поведения frontend и инфраструктурной конфигурации, а не после одной успешной сборки.

**Blocked by:** 37 — Проверка критических гарантий на PostgreSQL; 38 — Воспроизводимый и однозначно идентифицируемый релиз; 52 — Недельный черновик, устойчивый к поздним ответам и сетевым ошибкам.

**Status:** ready-for-agent

- [ ] Автоматизированы быстрые backend-тесты, PostgreSQL critical-suite, drift-guard миграций, frontend state-тесты и чистая release-сборка из lockfile.
- [ ] Гейт проверяет shell-инструменты, семантику конфигурации, Compose, Caddy и Collector; один bash syntax check не считается достаточным.
- [ ] Малый browser smoke проходит регистрацию/подтверждение, создание семьи/рецепта, план и покупки; анонимный просмотр ссылки и warning/broken проверены без изменения принятой семантики.
- [ ] Проверки соответствуют текущим опубликованным сценариям и легко включают новые регрессии по мере слияния остальных тикетов, без обязательного ожидания всего набора 36–72.
- [ ] Публикация release-образов запускается только после зелёного гейта; обычная проверка не требует production-секретов, не деплоит сервер и не публикует образы.
- [ ] Намеренная SQL-ошибка, frontend-гонка и неверная инфраструктурная конфигурация проваливают соответствующий этап с понятной диагностикой.
- [ ] Тесты используют управляемые время/ответы/коды и изолированное окружение, не полагаются на случайный неверный код или неопределённые sleep; ресурсы очищаются.
- [ ] Результаты и диагностические артефакты доступны без утечки писем/секретов; анализ зависимостей/образов сообщает конкретные findings и документированную политику их обработки.
- [ ] CI согласован с реально используемым хостингом репозитория и локальным контейнерным запуском; инструкция позволяет воспроизвести критические проверки без SDK на хосте.

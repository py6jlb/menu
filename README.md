# Меню для домохозяек

Веб-приложение для семейного планирования меню: рецепты, недельное планирование, список покупок.

Стек: .NET 10 Minimal APIs (backend), Vue 3 + Vite (SPA), Postgres, nginx. Всё поднимается Docker Compose.

## Структура

- `backend/` — приложение `src/MenuPlanner.Api` (Minimal APIs + EF Core + Postgres) и тесты `tests/MenuPlanner.Api.Tests` (xUnit, WebApplicationFactory).
- `frontend/` — Vue 3 + Vite SPA, собирается в статику и раздаётся nginx.
- `docker-compose.yml` — оркестрация: `db`, `backend`, `frontend`.
- `MenuPlanner.sln` — решение .NET в корне репозитория.

## Быстрый старт

Требуется Docker с плагином Compose (v2).

```bash
docker compose up --build
```

## Деплой

Прод — собственный VPS/VDS (Ubuntu 24.04 LTS) с Docker Compose: Caddy как единый край, своя Postgres, бэкапы в объектное хранилище, логи через OpenTelemetry. Наружу открыты только 80/443 и SSH.

Порядок и переменные — в [`deploy/README.md`](deploy/README.md):

Настройки скриптов: локально `deploy/local.conf`, на сервере `/opt/menu/server.conf`
(отдельные шаблоны в `deploy/`). Это literal-данные `KEY=value`, не shell source;
окружение имеет приоритет, включая явно пустые значения. Серверные ручные операции
Compose выполняются через `./deploy/compose.sh`, чтобы избежать автозагрузки `.env`.

```bash
sudo SSH_PUBLIC_KEY='ssh-ed25519 ...' ./deploy/bootstrap.sh   # настройка сервера
./deploy/build-push.sh --publish                              # сборка и публикация образов
./deploy/deploy.sh <git-sha>                                  # деплой (откат — тем же скриптом)
./deploy/smoke.sh                                             # проверка релиза на сервере
```

Сборка без `--publish` не публикует образы. Релиз привязан к чистому commit:
`build-push.sh` пишет `deploy/release/<tag>.json` (commit, дайджесты, версии
конфигурации, время сборки), `deploy.sh` выкатывает конфигурации этого коммита,
а `remote-deploy.sh` сохраняет выбранный тег в `/opt/menu/current-release` и
manifest в `/opt/menu/release.json`. Подробности — в [`deploy/README.md`](deploy/README.md).

Dev-стек остаётся прежним: `docker compose up --build`.

### Гейт релиза

Перед публикацией образы проходят единый автоматический гейт — одна успешная сборка публикацией не считается. Гейт запускается локально и не требует production-секретов (workflow `.github/workflows/release-gate.yml` оставлен для ручного запуска, авто-триггеры выключены):

```bash
scripts/release-gate.sh                  # быстрые этапы (shellcheck, deploy-suite, Compose/Caddy/Collector, backend, PostgreSQL, миграции, frontend, зависимости)
scripts/release-gate.sh --with-browser   # плюс сквозной browser smoke на полном стеке
scripts/release-gate.sh --list           # список этапов
```

На хосте нужен только Docker: .NET SDK, Node и Postgres не устанавливаются — этапы идут в контейнерах. Каждый этап пишет диагностику в `deploy/gate-artifacts/<этап>.log`; при провале гейт печатает этап, причину и путь к журналу. Намеренная SQL-ошибка проваливает `postgres`, гонка во frontend-тесте — `frontend`, неверная инфраструктурная конфигурация — `infra`. `build-push.sh` вызывает гейт перед сборкой и дополнительно browser smoke перед публикацией: `--publish` без зелёного гейта образы не публикует. Подробности и политика обработки findings — в [`deploy/README.md`](deploy/README.md#гейт-релиза).

Frontend-тесты (Vitest + jsdom, поведение черновика недели и черновика рецепта):


## PWA и офлайн

Приложение устанавливается как PWA и работает офлайн только для чтения. Service worker (`vite-plugin-pwa`) прекэширует оболочку и локальный шрифт Nunito; читающие API-ответы (список покупок, план, рецепты, семья, настройки, автодополнение, публичный просмотр по ссылке) кэшируются по стратегии network-first и доступны без сети. Аутентификация, админка и управление ссылками не кэшируются; кэш данных чистится при выходе и при `401`. Обновление версии предлагается баннером, а не применяется молча. Push-уведомлений нет.

Проверить офлайн: `npm run build && npm run preview` — в dev service worker отключён, чтобы не мешать HMR. Иконки приложения генерируются из `frontend/pwa-icon.svg` (монограмма «М»):

```bash
docker run --rm -u "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD":/app -w /app/frontend node:24 \
  npx --yes @vite-pwa/assets-generator@2.0.0 pwa-icon.svg --preset minimal --root .
# готовые png/ico из frontend/ перенести в frontend/public/
```

## Конфигурация backend

- Подключение БД: при заданном `DB_HOST` используется structured-набор `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` через `NpgsqlConnectionStringBuilder` (так работает prod-Compose, сохраняя literal-пароли). Без `DB_HOST` прежний приоритет: `ConnectionStrings:Default` (env `ConnectionStrings__Default` или JSON-default с `Host=db`) → `DB_CONNECTION_STRING` → fallback с `Host=localhost`. Dev-Compose и EF factory сохраняют прежние overrides без `DB_HOST`. Подробности и defaults — в [`deploy/README.md`](deploy/README.md#literal-параметры-подключения-backend).
- При старте применяются EF Core миграции (`MigrateAsync`) — схема БД обновляется автоматически. Новую миграцию генерируют из корня через SDK-контейнер:

  ```bash
  docker run --rm -v "$(pwd)":/app -w /app mcr.microsoft.com/dotnet/sdk:10.0 \
    sh -c "dotnet tool restore && dotnet ef migrations add <Name> --project backend/src/MenuPlanner.Api --startup-project backend/src/MenuPlanner.Api"
  ```

  **Разовая миграция при переходе:** если dev-БД была создана прежним `EnsureCreated`, пересоздать том — `docker compose down -v` и поднять заново.
- Папка фото: env `PHOTOS_DIR`, по умолчанию `./photos` (в контейнере — `/app/photos`, смонтирована как named volume `photos_data`, чтобы фото переживали пересоздание контейнера).
- Базовый URL ссылок шаринга: env `SHARE_BASE_URL` (необязательный). Если пусто — ссылка отдаётся относительной (`/r/{token}`) и разрешается фронтендом относительно текущего домена.
- Endpoint `GET /health` возвращает `200 {"status":"ok","service":"menu-planner-api","release":"<release-id>"}`; `release` — идентификатор релиза для корреляции (`unknown`, если manifest и `RELEASE_ID` недоступны).

### Наблюдаемость (логи и trace-id)

Backend пишет одну структурированную запись на запрос: operation (шаблон маршрута), статус, длительность, trace-id и release-id. Share-токены в пути минимизируются (`/api/shared/{token}`), тела запросов и секреты не логируются. Полные traces не хранятся согласованно, поэтому их OTLP-экспорт выключен; Activity и trace-id формируются всегда и связывают журналы. Логи уходят в `otel-collector` по OTLP и лежат в файле с ротацией по размеру/возрасту.

| Переменная | Описание |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Адрес OTLP-приёмника коллектора. Пусто — логи никуда не экспортируются |
| `OTEL_TRACES_EXPORT_ENABLED` | `true` включает экспорт полных traces (по умолчанию `false`: согласованного хранилища traces нет) |
| `RELEASE_ID` | Идентификатор релиза для журналов (в prod — закреплённый тег `IMAGE_TAG`) |
| `RELEASE_MANIFEST_PATH` | Путь к `release.json`; используется, только если `RELEASE_ID` не задан. Отсутствие файла не ломает приложение — release-id становится `unknown` |
| `OTEL_LOG_QUEUE_SIZE` | Размер буфера экспорта логов, `≥256` (по умолчанию `2048`): при недоступном коллекторе память не растёт неограниченно |
| `OTEL_LOG_BATCH_SIZE` | Размер пакета экспорта (по умолчанию `512`) |
| `OTEL_EXPORT_TIMEOUT_MS` | Тайм-аут экспорта, `1000..60000` (по умолчанию `10000`); экспорт идёт фоном и не блокирует запрос |


### Email (SMTP)

Письма (подтверждение почты, сброс пароля) отправляются через SMTP. Конфигурация — env-переменные (в `docker-compose.yml` прокинуты с дефолтами):

| Переменная | Описание |
|---|---|
| `SMTP_HOST` | Хост SMTP-сервера. Пустой — только явный dev/test-режим (`EMAIL_TRANSPORT=log`), SMTP не используется |
| `SMTP_PORT` | Порт (по умолчанию `587`) |
| `SMTP_USER`, `SMTP_PASSWORD` | Логин/пароль, если сервер требует аутентификацию |
| `SMTP_FROM` | Адрес отправителя (обязателен, если задан `SMTP_HOST`) |
| `SMTP_FROM_NAME` | Имя отправителя (по умолчанию «Меню для домохозяек») |
| `SMTP_SECURITY` | `starttls` (по умолчанию) — явно требуемый STARTTLS, типично порт 587; `ssl` — неявный TLS, типично порт 465 |
| `SMTP_TIMEOUT_SECONDS` | Предел ожидания SMTP-операций, 1–300 (по умолчанию `10`) |
| `EMAIL_TRANSPORT` | `smtp` (по умолчанию при заданном `SMTP_HOST`) или `log` — dev/test-запись полного письма в журнал |

Соединение всегда защищено: выбирается либо явно требуемый STARTTLS, либо неявный TLS, без даунгрейда «когда доступно» и без отключения проверки сертификата. Несовместимые host/port/TLS (`starttls` на 465, `ssl` на 587) и неполные поля (`SMTP_FROM`, пара `SMTP_USER`/`SMTP_PASSWORD`, порог тайм-аута) дают понятную ошибку конфигурации на старте; значения секретов в ней не печатаются. Устаревший `SMTP_ENABLE_STARTTLS=false` отвергается — отключать TLS нельзя.

Если `SMTP_HOST` не задан, SMTP не используется: полное письмо (адресат, отправитель, тема, HTML-тело с кодом) записывается в лог backend **только** в явном dev/test-режиме (`EMAIL_TRANSPORT=log`, либо lab с пустым SMTP). В production пустой SMTP и `EMAIL_TRANSPORT=log` запрещены, поэтому коды и HTML не попадают в production-журналы. Этот режим используется в тестах. Письма — простые HTML на русском, без вложений.

Сбой SMTP не считается доставкой: транзакция отправки ограничена `SMTP_TIMEOUT_SECONDS`, ошибка оборачивается безопасным результатом без учётных данных и тела письма.

### Очередь писем (надёжная доставка)

Принятая доставка не теряется при временном отказе SMTP. Создание аккаунта/выдача кода и запись «письмо принято к отправке» сохраняются **одной транзакцией** в PostgreSQL (маленький outbox, без отдельного брокера). Регистрация сразу возвращает сессию (`201 { token, user }`), а письмо доводит фоновая отправка: ограниченные повторы с растущей задержкой, периодический опрос и восстановление после перезапуска. Параллельные воркеры не обрабатывают одну запись дважды (захват строк `FOR UPDATE SKIP LOCKED` на PostgreSQL; необработанные зависшие захваты переоцениваются по сроку аренды).

Перед отправкой проверяются срок действия и актуальность кода: истёкший, потреблённый или заменённый challenge не отправляется как действующий. Если результат отправки неопределён (тайм-аут SMTP), повтор относится к тому же challenge и не создаёт новый код. Содержимое письма (одноразовый код) хранится в БД в защищённом виде: ключ выводится из `EMAIL_OUTBOX_KEY` (или, если не задан, из `JWT_SECRET` через HKDF) и переживает перезапуск. Код не логируется. Успешно отправленная запись удаляется сразу; окончательно проваленные хранятся ограниченный срок и затем удаляются.

Пользователь видит разницу между «запрос принят» и «доставлено»: экран подтверждения сообщает, что запрос принят, предлагает повторную отправку по таймеру и не заявляет ложный успех доставки. `/api/auth/forgot` по-прежнему отвечает нейтрально.

Необязательные параметры очереди (значения по умолчанию указаны): `EMAIL_OUTBOX_MAX_ATTEMPTS=6`, `EMAIL_OUTBOX_BATCH_SIZE=20`, `EMAIL_OUTBOX_RETRY_BASE_SECONDS=30`, `EMAIL_OUTBOX_MAX_DELAY_MINUTES=60`, `EMAIL_OUTBOX_LEASE_SECONDS=120`, `EMAIL_OUTBOX_RETENTION_DAYS=7`, `EMAIL_OUTBOX_POLL_SECONDS=15`, `EMAIL_OUTBOX_KEY` (ключ защиты, иначе выводится из `JWT_SECRET`).

## Аутентификация (JWT)

Пользователи регистрируются по email и паролю, входят по JWT. Роли: `User` и `Admin`. Публичная регистрация всегда выдаёт только `User`; системного `Admin` оператор создаёт закрытой командой `admin-bootstrap` до публичной регистрации (см. «Первый администратор»). Роль `Admin` — системная и не связана с владением семьёй.

При регистрации аккаунт создаётся сразу (`user.isEmailVerified=false`), и на почту ставится в очередь 6-значный код подтверждения. Код одноразовый, срок жизни 24 ч. Временная недоступность SMTP не мешает регистрации: сессия выдаётся сразу, письмо отправляется фоновой очередью.

Endpoints:

| Метод | Путь             | Описание                                            |
|-------|------------------|-----------------------------------------------------|
| POST  | `/api/auth/register` | `{ email, password }` → `201 { token, user }` (сессия после **принятия** письма к отправке, даже при временном отказе SMTP); дубликат email → `409`; код подтверждения ставится в надёжную очередь; rate limit 10/час на IP + 5/час на email → `429` |
| POST  | `/api/auth/login`    | `{ email, password }` → `200 { token, user }`; неверный пароль → `401`; rate limit 30/мин на IP + 10/мин на email → `429` |
| GET   | `/api/auth/me`       | `[Authorize]` — текущий пользователь (`Authorization: Bearer <token>`) |
| POST  | `/api/auth/verify`        | `[Authorize]` — `{ code }` → `200 { user }` (почта подтверждена); неверный/истёкший код → `400`; после 5 неверных попыток → `423` (блокировка); почта уже подтверждена → `409` |
| POST  | `/api/auth/verify/resend` | `[Authorize]` — новая выдача кода и постановка в очередь (`200` = запрос принят, доставка не гарантирована немедленно); повторный запрос раньше таймера (по умолчанию 5 мин) → `429`; rate limit 5/час на IP + 5/час на email → `429`; при блокировке попыток → `423` |
| POST  | `/api/auth/forgot`   | `{ email }` → `200 { message }` — всегда нейтральный ответ; код сброса уходит только если аккаунт существует и почта подтверждена; resend по таймеру (по умолчанию 5 мин); rate limit 5/час на IP + 5/час на email → `429` |
| POST  | `/api/auth/reset`    | `{ email, code, newPassword, newPasswordConfirm }` → `200 { message }`; неверный/истёкший код или неизвестный/неподтверждённый email → `400` (`code`: `invalid`/`expired`/`used`); исчерпание попыток закрывает конкретный код → `400` (`code: closed`), новый код доступен после таймера; смена пароля инкрементирует `TokenVersion`, ранее выданные токены → `401`; rate limit 10/час на IP + 10/час на email → `429` |
| POST  | `/api/admin/unlock`  | `[Authorize(Roles=Admin)]` — `{ email }` → `200 { message }`; сбрасывает счётчик попыток и `LockedUntil`; неизвестный email → `404`; rate limit 10/мин на администратора + 30/мин на IP → `429` |

Все ответы ограничителя — `429` с заголовком `Retry-After` (секунды). Лимитер — in-memory и действует на **одну реплику**; число ключей ограничено, устаревшие окна удаляются, а при переполнении новые ключи отклоняются, пока не освободится место (уже отслеживаемые окна не вытесняются). Порядок проверки — сначала IP, затем операция/email/пользователь: поток уникальных email с уже ограниченного адреса не создаёт новые ключи. Переход к общему хранилищу (например, Redis) при масштабировании — отдельное ограничение (см. `deploy/README.md`).

### Первый администратор

Системная роль `Admin` не выдаётся публичной регистрацией: первый случайный посетитель и конкурентные запросы не могут её занять. Первоначального администратора создаёт оператор закрытой командой вне публичного маршрута.

Dev (после `docker compose up --build`):

```bash
read -rsp 'Пароль администратора: ' ADMIN_PW; echo
printf '%s\n' "$ADMIN_PW" | docker compose run --rm --no-deps -T backend admin-bootstrap --email admin@example.com
unset ADMIN_PW
```

Prod (на сервере, через серверный Compose без автозагрузки `.env`):

```bash
read -rsp 'Пароль администратора: ' ADMIN_PW; echo
printf '%s\n' "$ADMIN_PW" | ./deploy/compose.sh run --rm --no-deps -T backend admin-bootstrap --email admin@example.com
unset ADMIN_PW
```

Пароль читается из stdin (на терминале — скрыто) и не попадает в аргументы командной строки, журналы и состояние контейнера. Команда идемпотентна: повторный запуск не создаёт второго администратора и не перезаписывает пароль существующего email; конкурентные запуски сериализуются advisory-блокировкой PostgreSQL. Созданный администратор остаётся неподтверждённым: введите код из письма (при неудаче доставки — запросите повторно через `/api/auth/verify/resend`). До подтверждения почты административные изменяющие операции недоступны; на существующей установке уже подтверждённые администраторы сохраняются и bootstrap их не трогает. Владелец семьи — это создатель семьи (`Family.Owner`), а не системная роль `Admin`.

### Коды подтверждения и сброса

Коды генерируются как 6 цифр и хранятся в хэшированном виде (`PasswordHasher`). Настройки — секция `AuthCode` в `appsettings.json`, переопределяются env-переменными:

| Переменная | Описание |
|---|---|
| `AUTH_CODE_MAX_ATTEMPTS` | Максимум неверных попыток ввода (по умолчанию `5`) |
| `AUTH_CODE_LOCK_DAYS` | Длительность блокировки подтверждения почты после исчерпания попыток в днях (по умолчанию `3`); сброс пароля аккаунт не блокирует |
| `AUTH_CODE_RESEND_COOLDOWN_MINUTES` | Таймер повторной отправки кода в минутах (по умолчанию `5`) |
| `AUTH_CODE_RESEND_RATE_LIMIT_PER_HOUR` | Rate limit повторной отправки в час (по умолчанию `5`) |

### Ограничение частоты и доверенный прокси

Настройки лимитов — секция `AuthRateLimit` в `appsettings.json`, переопределяются env-переменными. Значения проверяются на старте: нечисловое или неположительное значение — понятный отказ без раскрытия секретов.

| Переменная | Описание |
|---|---|
| `AUTH_RATE_LIMIT_LOGIN_PER_IP_PER_MINUTE` | Логин: попыток в минуту на IP (по умолчанию `30`) |
| `AUTH_RATE_LIMIT_LOGIN_PER_EMAIL_PER_MINUTE` | Логин: попыток в минуту на email (по умолчанию `10`) |
| `AUTH_RATE_LIMIT_REGISTER_PER_IP_PER_HOUR` | Регистрация: аккаунтов в час на IP (по умолчанию `10`) |
| `AUTH_RATE_LIMIT_REGISTER_PER_EMAIL_PER_HOUR` | Регистрация: попыток в час на email (по умолчанию `5`) |
| `AUTH_RATE_LIMIT_RESET_PER_IP_PER_HOUR` | Сброс пароля: запросов в час на IP (по умолчанию `10`) |
| `AUTH_RATE_LIMIT_RESET_PER_EMAIL_PER_HOUR` | Сброс пароля: запросов в час на email (по умолчанию `10`) |
| `AUTH_RATE_LIMIT_UNLOCK_PER_ADMIN_PER_MINUTE` | Разблокировка: запросов в минуту на администратора (по умолчанию `10`) |
| `AUTH_RATE_LIMIT_UNLOCK_PER_IP_PER_MINUTE` | Разблокировка: запросов в минуту на IP (по умолчанию `30`) |
| `AUTH_RATE_LIMIT_MAX_TRACKED_KEYS` | Максимум ключей в in-memory хранилище (по умолчанию `10000`) |

Клиентский IP берётся из `HttpContext.Connection.RemoteIpAddress` после `UseForwardedHeaders`. Доверенный прокси задаётся `TRUSTED_PROXY_ADDRESSES` (список IP) и/или `TRUSTED_PROXY_NETWORKS` (список CIDR). Если ничего не задано, middleware forwarded-заголовков не подключается, и сырой `X-Forwarded-For` игнорируется (пустой известный список ASP.NET Core иначе трактовал бы как «доверять всем»). В dev-стеке доверен только nginx (`172.28.0.10`), в prod — Caddy (`172.29.0.10`); значения прокинуты в `docker-compose.yml`/`docker-compose.prod.yml`.

Блокировка действует на операцию (не на вход): по истечении срока счётчик попыток сбрасывается. Это правило относится к подтверждению почты. Сброс пароля — анонимная операция: 5 неверных попыток закрывают только текущий код (`AuthCode.Attempts`), аккаунт не блокируется, новый код можно запросить после таймера; запросы без действующего кода не создают блокировку. Администратор (системная роль `Admin`, созданная закрытым bootstrap) может снять блокировку подтверждения досрочно через `/api/admin/unlock`; для этого его собственная почта должна быть подтверждена.

Восстановление пароля: `/forgot` принимает email и всегда отвечает нейтрально (не раскрывает существование и статус аккаунта). Код сброса отправляется только при подтверждённой почте, действует 1 час и одноразовый; повторный `/forgot` раньше таймера не шлёт новое письмо. Сброс — один запрос `/reset` (код + новый пароль + повтор). После смены пароля `TokenVersion` инкрементируется, поэтому все ранее выданные JWT перестают работать.

Пароли хранятся как хэш (`PasswordHasher<User>`, ASP.NET Identity), не в открытом виде. Секрет JWT задаётся в секции `Jwt` в `appsettings.json` (значение для разработки только!) и переопределяется env-переменными:

- `JWT_SECRET` — секрет подписи токена (минимум 32 символа, обязателен к смене в production).
- `JWT_ISSUER`, `JWT_AUDIENCE`, `JWT_EXPIRY_MINUTES`.

В `docker-compose.yml` для сервиса `backend` секрет подставляется из `JWT_SECRET` окружения хоста, иначе используется dev-значение.

## Семья

Семья — единица владения рецептами, планом и списком покупок. Пользователь состоит не более чем в одной семье (членство защищено уникальным индексом `FamilyMembers.UserId`). Создатель семьи — её владелец: только он перегенерирует инвайт-код и удаляет участников. Все endpoint'ы требуют авторизации; изменяющие операции дополнительно требуют подтверждённой почты (`403`).

| Метод | Путь | Описание |
|-------|------|----------|
| POST  | `/api/families` | `{ name }` → `201 FamilyDto` — создать семью, создатель становится владельцем. Пустое имя → `400`; уже состоит в семье → `409` |
| GET   | `/api/families/my` | Текущая семья пользователя; нет семьи → `404` |
| POST  | `/api/families/join` | `{ inviteCode }` → `200 FamilyDto`. Пустой код → `400`; уже состоит в семье → `409`; код не найден → `404` |
| POST  | `/api/families/{id}/invite-code/regenerate` | `200 { inviteCode }` — заменить код; не владелец / неподтверждённая почта → `403`; семья не найдена → `404` |
| DELETE| `/api/families/{id}/members/{userId}` | `204` — удалить участника; удаление владельца → `400`; не владелец / неподтверждённая почта → `403`; участник не найден → `404` |

Гонка уникального членства (два одновременных создания или вступления одного пользователя) разрешается уникальным индексом: проигравший запрос получает `409`, а не `500`, и не оставляет ложного локального состояния — в БД остаётся ровно одна семья и одно членство.

На странице семьи фронтенд ведёт отдельное состояние ошибки и ожидания для каждого действия (загрузка, создание, вступление, копирование кода, перегенерация, удаление участника). Ошибка одного действия не скрывает загруженную семью и формы: после неверного инвайт-кода значение можно исправить и повторить без перезагрузки, сбой копирования не убирает код, а сбой удаления не убирает список участников. Незавершённая сетевая операция всегда снимает ожидание, повтор доступен вручную, а повторные клики на мутациях не запускают конкурирующих запросов.

## Рецепты (CRUD)

Все endpoints рецептов требуют авторизации (`Authorization: Bearer <token>`) и ограничены семьёй текущего пользователя: любой член семьи видит и может редактировать/удалять общие рецепты.

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/recipes` | Список рецептов семьи (краткие поля, включая `seasonality` и `diet`) |
| GET  | `/api/recipes/{id}` | Полный рецепт (ингредиенты + шаги, включая `revision`); `404`, если рецепт не в семье пользователя |
| POST | `/api/recipes` | Создать рецепт (привязывается к семье пользователя); `404`, если пользователь не в семье |
| PUT  | `/api/recipes/{id}` | Полное обновление рецепта (поля, ингредиенты, шаги). Тело содержит `revision`; ревизия не передана → `400`, устарела → `409 { error, revision }` |
| DELETE | `/api/recipes/{id}?revision=N` | Удалить рецепт → `204`; без/с устаревшей ревизией → `400`/`409 { error, revision }`; внешний рецепт → `403` |
| DELETE | `/api/recipes/{id}/external?revision=N` | Убрать внешний рецепт из своей семьи → `204`; семья-источник не затрагивается; без/с устаревшей ревизией → `400`/`409`; обычный рецепт → `400` |
| POST | `/api/recipes/{id}/copy?revision=N` | Промоушен внешнего рецепта в копию: внешний рецепт становится обычным редактируемым рецептом (тот же `id`, записи плана не рвутся), контент и файл фото копируются, метка «скопировано из семьи X» сохраняется; без/с устаревшей ревизией → `400`/`409`; обычный рецепт → `400`; источник удалён (сломанная ссылка) → `400` |
| PUT  | `/api/recipes/{id}/photo?revision=N` | Загрузить фото рецепта (`multipart/form-data`, поле `file`); заменяет старое фото → `200` с рецептом; без/с устаревшей ревизией → `400`/`409` |
| DELETE | `/api/recipes/{id}/photo?revision=N` | Удалить фото → `204`; если фото нет — no-op `204` без роста ревизии; без/с устаревшей ревизией → `400`/`409` |
| GET  | `/api/photos/{fileName}` | Отдать файл фото (публично, без авторизации) |

Валидация (при ошибке → `400` с русским сообщением в поле `error`): название обязательно; хотя бы один шаг; время приготовления 1–1440 мин; порции 1–100; сложность 1–5; калорийность необязательна (0–10000); у ингредиента обязательны название, количество (> 0) и единица из справочника; примечание необязательно и не участвует в расчёте.

Ревизия рецепта (`revision`, старт `1`) — целое число, растущее на каждую успешную правку контента, фото, промоушен или удаление. `GET /api/recipes/{id}` возвращает её; `PUT`/`DELETE`/`copy`/фото принимают ожидаемую ревизию и атомарно проверяют её вместе с изменением (ревизия — токен конкурентности EF Core). Устаревшее изменение → `409 { error, revision }` с актуальной серверной версией, без частичной перезаписи; отсутствие ревизии → `400`. Удаление фото без фото — идемпотентный no-op, ревизия не растёт.

Хранение: шаги (`RecipeSteps`) и ингредиенты (`RecipeIngredients`) — дочерние таблицы с полем `Order`. Теги, сезонность и диета — нативные массивы Postgres (`text[]`). Единицы — фиксированный справочник кодов: `g, kg, ml, l, pcs, glass, tbsp, tsp, pinch` (г, кг, мл, л, шт, стакан, ст. ложка, ч. ложка, щепотка). Сезоны: `winter, spring, summer, autumn`.

### Фото рецептов

Файл хранится на диске сервера в папке `PHOTOS_DIR` под уникальным именем `{recipeId}-{guid}.{ext}`; в БД сохраняется только имя файла (`Recipe.PhotoPath`), URL отдаётся в ответах как `photoUrl` (null, если фото нет). При замене или удалении фото старый файл удаляется с диска; удаление рецепта также удаляет его файл.

Загрузка (`PUT /api/recipes/{id}/photo`) — авторизованный, семейный endpoint. Валидация: content-type из списка `image/jpeg`, `image/png`, `image/webp`, `image/gif`; размер не более 5 МБ; пустой файл → `400`. Загрузка/удаление принимают `?revision=N` и на устаревшей ревизии возвращают `409`; рецепт чужой семьи → `404`.

Отдача файла — `GET /api/photos/{fileName}` без авторизации: имя файла — случайный GUID, угадать его практически невозможно (трейдофф: любой, у кого есть URL, может открыть фото; если понадобится строгая приватность — добавить авторизацию на этот endpoint и токен на стороне клиента). Файл отдаётся через `Results.File`, content-type определяется по расширению.

Форма на фронтенде позволяет выбрать фото (с предпросмотром) до сохранения рецепта; загрузка/удаление выполняются после сохранения рецепта. Если фото выбрано, но не загрузилось — текст рецепта уже сохранён: пользователь видит частичный успех и может повторить **только** действие с фото, не создавая второй рецепт; при конфликте ревизии предлагается загрузить актуальную версию.

### Шаринг рецептов по ссылке

Участник семьи на детальной странице рецепта читает существующую ссылку вида `/r/{token}` и явно создаёт её кнопкой «Поделиться». Чтение (`GET`) никогда не создаёт запись и не открывает публичный доступ: при её отсутствии приходит `404`. Одна запись `RecipeShare` на рецепт. Создание доступно любому участнику семьи-источника с подтверждённой почтой; отзыв и перегенерация — только Владельцу семьи с подтверждённой почтой.

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/recipes/{id}/share` | `[Authorize]` — вернуть существующую ссылку. Любой участник семьи-источника; ссылка ещё не создана, рецепт чужой семьи или пользователь без семьи → `404`; внешний рецепт → `403`; без токена → `401` |
| POST | `/api/recipes/{id}/share` | `[Authorize]` + подтверждённая почта — явно создать ссылку: `201` при создании, `200` с той же ссылкой, если она уже есть. Любой участник семьи-источника; неподтверждённая почта или внешний рецепт → `403`; рецепт чужой семьи / без семьи → `404`. Параллельное первое создание сохраняет одну ссылку: проигравший гонку получает `200` с уже созданной ссылкой, а не `500` |
| DELETE | `/api/recipes/{id}/share` | `[Authorize]` + подтверждённая почта, только владелец семьи — отозвать ссылку (`revoked=true`); повторный отзыв идемпотентен (`200`); не владелец / неподтверждённая почта → `403`; ссылка ещё не создана → `404` |
| POST | `/api/recipes/{id}/share/regenerate` | `[Authorize]` + подтверждённая почта, только владелец семьи — заменить токен, старый становится недействителен; не владелец / неподтверждённая почта → `403`; ссылка ещё не создана → `404` |
| GET  | `/api/shared/{token}` | Без авторизации — живой полный рецепт семьи-источника (все поля + `photoUrl`); правки источника видны при повторном открытии. Несуществующий или отозванный токен, удалённый источник → `404` «Ссылка недействительна.» |
| POST | `/api/shared/{token}/import` | `[Authorize]` (нужна подтверждённая почта) — добавить внешний рецепт в свою семью → `201 { recipeId }`. Неподтверждённая почта → `403`; пользователь без семьи → `404`; рецепт уже добавлен, в том числе при гонке импортов → `409 { error, recipeId }` с id существующего внешнего рецепта; рецепт своей семьи → `400`; недействительный токен → `404`. Источник не копируется: владение и правки остаются у семьи-источника |

Ответ `.../share`: `{ recipeId, token, url, path, createdAt, revoked, revokedAt }`. `path` — `/r/{token}`; `url` — абсолютный, если задан `SHARE_BASE_URL`, иначе совпадает с `path`. Фронтенд-маршрут `/r/{token}` — публичный (без `requiresAuth`): рецепт показывается только для чтения, неавторизованному посетителю — мягкое приглашение войти (ссылки «Вход»/«Регистрация»).

### Состояния внешних рецептов

Внешний рецепт — рецепт в семье-получателе (`isExternal=true`, `sourceFamilyName`), контент которого читается живьём из семьи-источника; добавление — `POST /api/shared/{token}/import`, из своей семьи кнопка «Добавить» не показывается, повторное добавление → `409` (см. ADR-0005). В ответах `GET /api/recipes`, `GET /api/recipes/{id}`, `GET /api/plans/week/{weekStart}` есть поле `state`:

- `ok` — источник жив, ссылка актуальна;
- `warning` — источник жив, но ссылка отозвана/перегенерирована: контент ещё доступен, на детальной странице — баннер и CTA «Сделать копию, чтобы сохранить»;
- `broken` — источник удалил рецепт: остаётся только кэш имени, содержимое недоступно, рецепт помечен «недоступно», исключён из списка покупок, в плане — «убрать или заменить».

Участник может убрать внешний рецепт из своей семьи локально (`DELETE /api/recipes/{id}/external`) или сохранить его копией, чтобы редактировать (`POST /api/recipes/{id}/copy`); источник при этом не изменяется. Транзитивный шеринг и обычное редактирование/удаление внешних запрещены (`403`). В `GET /api/recipes` есть фильтр `scope=all|own|external`, в кратких и полных ответах — `isExternal` и `sourceFamilyName`.

## Автодополнение ингредиентов

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/ingredients/autocomplete?q=<text>` | `[Authorize]`, ограничен семьёй пользователя. Возвращает `{ "items": ["имя1", "имя2", ...] }` — до 10 различных названий ингредиентов из рецептов семьи, совпадающих с `q` по префиксу нормализованного названия (trim + нижний регистр, регистронезависимо). Сортировка: по частоте использования (убывание), затем по названию. |

Пустой/пустой-по-пробелам `q` возвращает самые используемые названия (топ), чтобы форма могла показывать подсказки до начала ввода. Пользователь без семьи получает пустой список (`{ "items": [] }`).

## Планирование недели

План семьи на неделю: сетка «7 дней × 5 приёмов пищи». Один план на семью на неделю; план создаётся с нуля (автогенерации нет). Все endpoints требуют авторизации и ограничены семьёй текущего пользователя; `404`, если пользователь не в семье.

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/plans/week/{weekStart}` | План недели: `{ weekStart, revision, entries: [{ day, mealType, recipeId, recipeName, portions, state }] }`; `state` — состояние внешнего рецепта (`ok`/`warning`/`broken`), `null` для своих; если плана нет — `200` с `revision: 0` и пустым `entries` (не создаётся) |
| PUT  | `/api/plans/week/{weekStart}` | Upsert всей недели с контролем ревизии: `expectedRevision: 0` создаёт план, `expectedRevision = revision` заменяет все записи недели (delete-and-insert) и увеличивает ревизию. Тело: `{ expectedRevision, entries: [{ day, mealType, recipeId, portions }] }`. Устаревшая ревизия → `409 { error, weekStart, revision, entries }` с текущей серверной версией, без частичной перезаписи |
| DELETE | `/api/plans/week/{weekStart}?expectedRevision=N` | Удаляет план недели вместе с записями → `204`. Без ревизии на существующем плане или при устаревшей ревизии → `409` с текущей версией; повторное удаление (плана уже нет) идемпотентно → `204` |

Ревизия (`revision`) — целое число, растёт с каждым сохранением и относится ко всей неделе. Чтение возвращает её, сохранение и удаление атомарно проверяют ожидаемую ревизию вместе с полной заменой/удалением записей: два PUT от одной ревизии дают один успех и один согласованный конфликт, а не смешение двух наборов записей. У отсутствующего плана исходная ревизия `0` — условие создания. Сетевой сбой не сдвигает ожидаемую ревизию, поэтому повтор проверяет ту же версию и не перезаписывает чужую работу.

`weekStart` — дата понедельника в формате `yyyy-MM-dd` (не понедельник → `400`). Названия рецептов подставляются сервером.

Коды приёмов пищи (i18n-дружественные строки; русские подписи — на фронте): `breakfast`, `snack_1`, `lunch`, `snack_2`, `dinner` (завтрак/перекус/обед/перекус/ужин — два перекуса различаются позицией в сетке). Дни недели: `day` 0–6, где 0 = понедельник … 6 = воскресенье.

Валидация (ошибка → `400` с русским сообщением в поле `error`): `day` 0–6; `mealType` из набора кодов; `portions` 1–100; рецепт принадлежит семье; не более одной записи на (день, приём пищи). Удаление рецепта каскадно удаляет записи плана, где он используется.

## Список покупок

Список покупок генерируется из плана недели: ингредиенты всех записей плана масштабируются коэффициентом `portions / рецепт.servings` и агрегируются. Эндпоинт требует авторизации и ограничен семьёй текущего пользователя.

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/shopping-list?weekStart={weekStart}` | Список покупок на неделю: `{ weekStart, hasPlan, items: [{ name, amount, unit, display, category }], excluded: [{ day, mealType, recipeId, recipeName, reason }] }`; `category` — код категории продукта или `null` («Прочее»); рецепты с состоянием `broken` (источник удалён) исключаются из `items` и возвращаются в `excluded`; `hasPlan` отличает отсутствующий план (`false`) от пустого (`true`) |

`weekStart` — дата понедельника в формате `yyyy-MM-dd` (не понедельник → `400`). Пользователь без семьи → `404`.

`excluded` — диагностика полноты: записи плана, которые не удалось посчитать. Сейчас единственная причина — `reason: "source_missing"` (рецепт-источник внешней ссылки удалён): такая запись исключается из сумм, её устаревшие ингредиенты не подставляются. Это отличает план только из недоступных блюд (`items` пуст, `excluded` непуст) от отсутствующего (`hasPlan: false`) и пустого (`hasPlan: true`, оба списка пусты).

### Форма позиции

`{ "name": "мука", "amount": 450, "unit": "g", "display": "450 г" }` — `name` — имя продукта (первое написание, встреченное в плане), `amount` — числовое количество (decimal, точки, без округления), `unit` — код итоговой единицы, `display` — готовый русский текст количества (например `"1.5 л"`, `"2 шт"`, `"3 ст. ложки"`). Бытовая мера остаётся отдельной строкой с единицей из справочника (`"соль"` + `"tsp"` + `"2 ч. ложки"`), а не вшивается в имя.

### Группировка и объединение

Название нормализуется как `Trim().ToLowerInvariant()`. Позиции объединяются по ключу «нормализованное имя + группа единицы»:

- **Вес** (`g`, `kg`) — конвертируются в граммы и суммируются; при итоге `≥ 1000` выводятся в кг, иначе в г.
- **Объём** (`ml`, `l`) — конвертируются в миллилитры и суммируются; при итоге `≥ 1000` выводятся в литрах, иначе в мл.
- **Штуки** (`pcs`) — просто суммируются.
- **Бытовые меры** (`glass`, `tbsp`, `tsp`, `pinch`) — не конвертируются; разные бытовые меры не объединяются; одинаковая мера + то же имя суммируется сырыми числами.

Продукты с одинаковым нормализованным именем, но разными группами единиц (например `"мука"` 300 г в одном рецепте и `"мука"` 1 стакан в другом) — **отдельные строки**: весовая строка + строка бытовой меры, так как их нельзя корректно свести.

### Масштабирование и вывод

`scaledAmount = amount * (portions / рецепт.servings)` — `portions` всегда берётся из записи плана (`PlanEntry.Portions`), `servings` рецепта — делитель. Каждая запись плана вносит свой вклад: один и тот же рецепт в двух слотах масштабируется по своим порциям в каждом. Пустые слоты ничего не добавляют.

Округление не применяется: `amount` хранит сырое значение. Вывод `display` обрезает хвостовые нули (`2.50` → `2.5`), десятичный разделитель — точка (`"1.5 л"`); дробные количества показываются как есть (`0.5`, `1.5`). Для бесконечных десятичных дробей (например `1/3`) вывод ограничен 10 знаками после запятой. Русские формы бытовых мер склоняются (`1 ст. ложка`, `2 ч. ложки`, `5 стаканов`, дробные — `1.5 стакана`).

### Критические гарантии PostgreSQL

Узкий suite поверх настоящего PostgreSQL проверяет то, что EF InMemory не воспроизводит: штатные миграции пустой БД и повторный запуск без потери данных, уникальность членства/недели/записи плана/ссылки и частичный индекс внешнего рецепта, внешние ключи и каскадное удаление, round-trip и диапазон `numeric(10,2)` ингредиента. Suite запускается в контейнерах, на хосте .NET SDK и Postgres не нужны:

```bash
scripts/test-postgres.sh
```

Скрипт поднимает одноразовый `postgres:16` в изолированной Docker-сети (без порта и volume), создаёт на каждый тест отдельную БД и удаляет её после — dev-БД и рабочие данные не затрагиваются. Без `MENU_PLANNER_TEST_POSTGRES` (или вне скрипта) PostgreSQL-тесты пропускаются, и быстрый `dotnet test` остаётся прежним. Для проверок гонок в suite есть `AsyncBarrier` — детерминированная точка пересечения независимых контекстов без случайных задержек; так управляемо воспроизводятся потребление кода, счётчик попыток, выдача/повторная выдача и разблокировка для подтверждения почты и сброса пароля.

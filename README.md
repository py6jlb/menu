# Меню для домохозяек

Веб-приложение для семейного планирования меню: рецепты, недельное планирование, список покупок.

Стек: .NET 10 Minimal APIs (backend), Vue 3 + Vite (SPA), Postgres, nginx. Всё поднимается Docker Compose.

## Структура

- `backend/` — приложение `src/MenuPlanner.Api` (Minimal APIs + EF Core + Postgres) и тесты `tests/MenuPlanner.Api.Tests` (xUnit, WebApplicationFactory).
- `frontend/` — Vue 3 + Vite SPA, собирается в статику и раздаётся nginx.
- `docker-compose.yml` — оркестрация: `db`, `backend`, `frontend`.
- `MenuPlanner.sln` — решение .NET в корне репозитория.

## Конфигурация backend

- Строка подключения: env `ConnectionStrings__Default` (или `DB_CONNECTION_STRING`), при отсутствии — дефолт `Host=localhost;...` в `appsettings.json`.
- При старте применяются EF Core миграции (`MigrateAsync`) — схема БД обновляется автоматически. Новую миграцию генерируют из корня через SDK-контейнер:

  ```bash
  docker run --rm -v "$(pwd)":/app -w /app mcr.microsoft.com/dotnet/sdk:10.0 \
    sh -c "dotnet tool restore && dotnet ef migrations add <Name> --project backend/src/MenuPlanner.Api --startup-project backend/src/MenuPlanner.Api"
  ```

  **Разовая миграция при переходе:** если dev-БД была создана прежним `EnsureCreated`, пересоздать том — `docker compose down -v` и поднять заново.
- Папка фото: env `PHOTOS_DIR`, по умолчанию `./photos` (в контейнере — `/app/photos`, смонтирована как named volume `photos_data`, чтобы фото переживали пересоздание контейнера).
- Базовый URL ссылок шаринга: env `SHARE_BASE_URL` (необязательный). Если пусто — ссылка отдаётся относительной (`/r/{token}`) и разрешается фронтендом относительно текущего домена.
- Endpoint `GET /health` возвращает `200 {"status":"ok"}`.

### Email (SMTP)

Письма (подтверждение почты, сброс пароля) отправляются через SMTP. Конфигурация — env-переменные (в `docker-compose.yml` прокинуты с пустыми дефолтами):

| Переменная | Описание |
|---|---|
| `SMTP_HOST` | Хост SMTP-сервера. Пустой (по умолчанию) — SMTP не используется |
| `SMTP_PORT` | Порт (по умолчанию `587`) |
| `SMTP_USER`, `SMTP_PASSWORD` | Логин/пароль, если сервер требует аутентификацию |
| `SMTP_FROM` | Адрес отправителя (обязателен, если задан `SMTP_HOST`) |
| `SMTP_FROM_NAME` | Имя отправителя (по умолчанию «Меню для домохозяек») |
| `SMTP_ENABLE_STARTTLS` | Включить STARTTLS (по умолчанию `true`) |

Если `SMTP_HOST` не задан (dev), отправка не выполняется: письмо (адресат, отправитель, тема, HTML-тело) записывается в лог backend. Этот режим используется в тестах. Письма — простые HTML на русском, без вложений.

## Аутентификация (JWT)

Пользователи регистрируются по email и паролю, входят по JWT. Роли: `User` и `Admin`. **Первый зарегистрированный пользователь становится Admin**, остальные — `User`.

При регистрации аккаунт создаётся сразу (`user.isEmailVerified=false`) и на почту отправляется 6-значный код подтверждения. Код одноразовый, срок жизни 24 ч.

Endpoints:

| Метод | Путь             | Описание                                            |
|-------|------------------|-----------------------------------------------------|
| POST  | `/api/auth/register` | `{ email, password }` → `201 { token, user }`; дубликат email → `409`; на почту уходит код подтверждения |
| POST  | `/api/auth/login`    | `{ email, password }` → `200 { token, user }`; неверный пароль → `401` |
| GET   | `/api/auth/me`       | `[Authorize]` — текущий пользователь (`Authorization: Bearer <token>`) |
| POST  | `/api/auth/verify`        | `[Authorize]` — `{ code }` → `200 { user }` (почта подтверждена); неверный/истёкший код → `400`; после 5 неверных попыток → `423` (блокировка); почта уже подтверждена → `409` |
| POST  | `/api/auth/verify/resend` | `[Authorize]` — повторная отправка кода; повторный запрос раньше таймера (по умолчанию 5 мин) → `429`; rate limit 5 запросов/час на email + на IP → `429`; при блокировке попыток → `423` |
| POST  | `/api/auth/forgot`   | `{ email }` → `200 { message }` — всегда нейтральный ответ; код сброса уходит только если аккаунт существует и почта подтверждена; resend по таймеру (по умолчанию 5 мин); rate limit 5 запросов/час на email + на IP → `429` |
| POST  | `/api/auth/reset`    | `{ email, code, newPassword, newPasswordConfirm }` → `200 { message }`; неверный/истёкший код или неизвестный/неподтверждённый email → `400`; после 5 неверных попыток → `423`; смена пароля инкрементирует `TokenVersion`, ранее выданные токены → `401` |
| POST  | `/api/admin/unlock`  | `[Authorize(Roles=Admin)]` — `{ email }` → `200 { message }`; сбрасывает счётчик попыток и `LockedUntil`; неизвестный email → `404`; rate limit 10 запросов/мин на администратора → `429` |

### Коды подтверждения и сброса

Коды генерируются как 6 цифр и хранятся в хэшированном виде (`PasswordHasher`). Настройки — секция `AuthCode` в `appsettings.json`, переопределяются env-переменными:

| Переменная | Описание |
|---|---|
| `AUTH_CODE_MAX_ATTEMPTS` | Максимум неверных попыток ввода (по умолчанию `5`) |
| `AUTH_CODE_LOCK_DAYS` | Длительность блокировки после исчерпания попыток в днях (по умолчанию `3`) |
| `AUTH_CODE_RESEND_COOLDOWN_MINUTES` | Таймер повторной отправки кода в минутах (по умолчанию `5`) |
| `AUTH_CODE_RESEND_RATE_LIMIT_PER_HOUR` | Rate limit повторной отправки в час (по умолчанию `5`) |

Блокировка действует на операцию (не на вход): по истечении срока счётчик попыток сбрасывается. Администратор (роль `Admin`, первый зарегистрированный пользователь) может снять блокировку досрочно через `/api/admin/unlock`.

Восстановление пароля: `/forgot` принимает email и всегда отвечает нейтрально (не раскрывает существование и статус аккаунта). Код сброса отправляется только при подтверждённой почте, действует 1 час и одноразовый; повторный `/forgot` раньше таймера не шлёт новое письмо. Сброс — один запрос `/reset` (код + новый пароль + повтор). После смены пароля `TokenVersion` инкрементируется, поэтому все ранее выданные JWT перестают работать.

Пароли хранятся как хэш (`PasswordHasher<User>`, ASP.NET Identity), не в открытом виде. Секрет JWT задаётся в секции `Jwt` в `appsettings.json` (значение для разработки только!) и переопределяется env-переменными:

- `JWT_SECRET` — секрет подписи токена (минимум 32 символа, обязателен к смене в production).
- `JWT_ISSUER`, `JWT_AUDIENCE`, `JWT_EXPIRY_MINUTES`.

В `docker-compose.yml` для сервиса `backend` секрет подставляется из `JWT_SECRET` окружения хоста, иначе используется dev-значение.

## Рецепты (CRUD)

Все endpoints рецептов требуют авторизации (`Authorization: Bearer <token>`) и ограничены семьёй текущего пользователя: любой член семьи видит и может редактировать/удалять общие рецепты.

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/recipes` | Список рецептов семьи (краткие поля) |
| GET  | `/api/recipes/{id}` | Полный рецепт (ингредиенты + шаги); `404`, если рецепт не в семье пользователя |
| POST | `/api/recipes` | Создать рецепт (привязывается к семье пользователя); `404`, если пользователь не в семье |
| PUT  | `/api/recipes/{id}` | Полное обновление рецепта (поля, ингредиенты, шаги) |
| DELETE | `/api/recipes/{id}` | Удалить рецепт → `204`; внешний рецепт → `403` |
| DELETE | `/api/recipes/{id}/external` | Убрать внешний рецепт из своей семьи → `204`; семья-источник не затрагивается; обычный рецепт → `400` |
| POST | `/api/recipes/{id}/copy` | Промоушен внешнего рецепта в копию: внешний рецепт становится обычным редактируемым рецептом (тот же `id`, записи плана не рвутся), контент и файл фото копируются, метка «скопировано из семьи X» сохраняется; обычный рецепт → `400`; источник удалён (сломанная ссылка) → `400` |
| PUT  | `/api/recipes/{id}/photo` | Загрузить фото рецепта (`multipart/form-data`, поле `file`); заменяет старое фото → `200` с рецептом |
| DELETE | `/api/recipes/{id}/photo` | Удалить фото → `204` |
| GET  | `/api/photos/{fileName}` | Отдать файл фото (публично, без авторизации) |

Валидация (при ошибке → `400` с русским сообщением в поле `error`): название обязательно; хотя бы один шаг; время приготовления 1–1440 мин; порции 1–100; сложность 1–5; калорийность необязательна (0–10000); у ингредиента обязательны название, количество (> 0) и единица из справочника; примечание необязательно и не участвует в расчёте.

Хранение: шаги (`RecipeSteps`) и ингредиенты (`RecipeIngredients`) — дочерние таблицы с полем `Order`. Теги, сезонность и диета — нативные массивы Postgres (`text[]`). Единицы — фиксированный справочник кодов: `g, kg, ml, l, pcs, glass, tbsp, tsp, pinch` (г, кг, мл, л, шт, стакан, ст. ложка, ч. ложка, щепотка). Сезоны: `winter, spring, summer, autumn`.

### Фото рецептов

Файл хранится на диске сервера в папке `PHOTOS_DIR` под уникальным именем `{recipeId}-{guid}.{ext}`; в БД сохраняется только имя файла (`Recipe.PhotoPath`), URL отдаётся в ответах как `photoUrl` (null, если фото нет). При замене или удалении фото старый файл удаляется с диска; удаление рецепта также удаляет его файл.

Загрузка (`PUT /api/recipes/{id}/photo`) — авторизованный, семейный endpoint. Валидация: content-type из списка `image/jpeg`, `image/png`, `image/webp`, `image/gif`; размер не более 5 МБ; пустой файл → `400`. Рецепт чужой семьи → `404`.

Отдача файла — `GET /api/photos/{fileName}` без авторизации: имя файла — случайный GUID, угадать его практически невозможно (трейдофф: любой, у кого есть URL, может открыть фото; если понадобится строгая приватность — добавить авторизацию на этот endpoint и токен на стороне клиента). Файл отдаётся через `Results.File`, content-type определяется по расширению.

Форма на фронтенде позволяет выбрать фото (с предпросмотром) до сохранения рецепта; загрузка/удаление выполняются после сохранения рецепта. Если фото выбрано, но не загрузилось — рецепт всё равно сохраняется, фото можно добавить повторно через редактирование.

### Шаринг рецептов по ссылке

Любой участник семьи на детальной странице рецепта может получить ссылку вида `/r/{token}` и скопировать её. Одна запись `RecipeShare` на рецепт; первое «Поделиться» создаёт токен, повторный запрос возвращает ту же ссылку. Владелец семьи может отозвать ссылку (запрет новых добавлений) или перегенерировать её (старая перестаёт работать, появляется новая).

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/recipes/{id}/share` | `[Authorize]` — создать (при отсутствии) или вернуть ссылку. Любой участник семьи-источника; рецепт чужой семьи или пользователь без семьи → `404`; без токена → `401` |
| DELETE | `/api/recipes/{id}/share` | `[Authorize]`, только владелец семьи — отозвать ссылку (`revoked=true`); не владелец → `403`; ссылка ещё не создана → `404` |
| POST | `/api/recipes/{id}/share/regenerate` | `[Authorize]`, только владелец семьи — отозвать старую и выдать новую; не владелец → `403` |
| GET  | `/api/shared/{token}` | Без авторизации — живой полный рецепт семьи-источника (все поля + `photoUrl`); правки источника видны при повторном открытии. Несуществующий или отозванный токен, удалённый источник → `404` «Ссылка недействительна.» |
| POST | `/api/shared/{token}/import` | `[Authorize]` (нужна подтверждённая почта) — добавить внешний рецепт в свою семью → `201 { recipeId, alreadyAdded }`. Неподтверждённая почта → `403`; пользователь без семьи → `404`; рецепт уже добавлен, в том числе при гонке импортов → `409 { error, recipeId }` с id существующего внешнего рецепта; рецепт своей семьи → `400`; недействительный токен → `404`. Источник не копируется: владение и правки остаются у семьи-источника |

Ответ `.../share`: `{ recipeId, token, url, path, createdAt, revoked, revokedAt }`. `path` — `/r/{token}`; `url` — абсолютный, если задан `SHARE_BASE_URL`, иначе совпадает с `path`. Фронтенд-маршрут `/r/{token}` — публичный (без `requiresAuth`): рецепт показывается только для чтения, неавторизованному посетителю — мягкое приглашение войти (ссылки «Вход»/«Регистрация»).

### Состояния внешних рецептов

Внешний рецепт — рецепт в семье-получателе (`isExternal=true`, `sourceFamilyName`), контент которого читается живьём из семьи-источника; добавление — `POST /api/shared/{token}/import`, из своей семьи кнопка «Добавить» не показывается, повторное добавление → `409` (см. ADR-0005). В ответах `GET /api/recipes`, `GET /api/recipes/{id}`, `GET /api/plans/week/{weekStart}` есть поле `state`:

- `ok` — источник жив, ссылка актуальна;
- `warning` — источник жив, но ссылка отозвана/перегенерирована: контент ещё доступен, на детальной странице — баннер и CTA «Сделать копию, чтобы сохранить»;
- `broken` — источник удалил рецепт: остаётся только кэш имени, содержимое недоступно, рецепт помечен «недоступно», исключён из списка покупок, в плане — «убрать или заменить».

Участник может убрать внешний рецепт из своей семьи локально (`DELETE /api/recipes/{id}/external`) или сохранить его копией, чтобы редактировать (`POST /api/recipes/{id}/copy`); источник при этом не изменяется. Транзитивный шеринг и обычное редактирование/удаление внешних запрещены (`403`). В `GET /api/recipes` есть фильтр `scope=all|own|external`, в кратких и полных ответах — `isExternal` и `sourceFamilyName`.

## Автодополнение ингредиентов

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/ingredients/autocomplete?q=<text>` | `[Authorize]`, ограничен семьёй пользователя. Возвращает `{ "items": ["имя1", "имя2", ...] }` — до 10 различных названий ингредиентов из рецептов семьи, совпадающих с `q` по префиксу нормализованного названия (trim + нижний регистр, регистронезависимо). Сортировка: по частоте использования (убывание), затем по названию. |

Пустой/пустой-по-пробелам `q` возвращает самые используемые названия (топ), чтобы форма могла показывать подсказки до начала ввода. Пользователь без семьи получает пустой список (`{ "items": [] }`).

## Планирование недели

План семьи на неделю: сетка «7 дней × 5 приёмов пищи». Один план на семью на неделю; план создаётся с нуля (автогенерации нет). Все endpoints требуют авторизации и ограничены семьёй текущего пользователя; `404`, если пользователь не в семье.

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/plans/week/{weekStart}` | План недели: `{ weekStart, entries: [{ day, mealType, recipeId, recipeName, portions, state }] }`; `state` — состояние внешнего рецепта (`ok`/`warning`/`broken`), `null` для своих; если плана нет — `200` с пустым `entries` (не создаётся) |
| PUT  | `/api/plans/week/{weekStart}` | Upsert всей недели: создаёт план при отсутствии и заменяет все записи недели (delete-and-insert). Тело: `{ entries: [{ day, mealType, recipeId, portions }] }` |
| DELETE | `/api/plans/week/{weekStart}` | Удаляет план недели вместе с записями → `204` (идемпотентно) |

`weekStart` — дата понедельника в формате `yyyy-MM-dd` (не понедельник → `400`). Названия рецептов подставляются сервером.

Коды приёмов пищи (i18n-дружественные строки; русские подписи — на фронте): `breakfast`, `snack_1`, `lunch`, `snack_2`, `dinner` (завтрак/перекус/обед/перекус/ужин — два перекуса различаются позицией в сетке). Дни недели: `day` 0–6, где 0 = понедельник … 6 = воскресенье.

Валидация (ошибка → `400` с русским сообщением в поле `error`): `day` 0–6; `mealType` из набора кодов; `portions` 1–100; рецепт принадлежит семье; не более одной записи на (день, приём пищи). Удаление рецепта каскадно удаляет записи плана, где он используется.

## Список покупок

Список покупок генерируется из плана недели: ингредиенты всех записей плана масштабируются коэффициентом `portions / рецепт.servings` и агрегируются. Эндпоинт требует авторизации и ограничен семьёй текущего пользователя.

| Метод | Путь | Описание |
|-------|------|----------|
| GET  | `/api/shopping-list?weekStart={weekStart}` | Список покупок на неделю: `{ weekStart, items: [{ name, amount, unit, display }] }`; рецепты с состоянием `broken` (источник удалён) исключаются; если плана нет — `200` с пустым `items` |

`weekStart` — дата понедельника в формате `yyyy-MM-dd` (не понедельник → `400`). Пользователь без семьи → `404`.

### Форма позиции

`{ "name": "мука", "amount": 450, "unit": "g", "display": "450 г" }` — `name` — имя продукта (первое написание, встреченное в плане), `amount` — числовое количество (decimal, точки, без округления), `unit` — код итоговой единицы, `display` — готовый русский текст количества (например `"1.5 л"`, `"2 шт"`, `"3 ст. ложки"`). Бытовая мера остаётся отдельной строкой с единицей из справочника (`"соль"` + `"tsp"` + `"2 ч. ложки"`), а не вшивается в имя.

### Группировка и объединение

Название нормализуется как `Trim().ToLowerInvariant()`. Позиции объединяются по ключу «нормализованное имя + группа единицы»:

- **Вес** (`g`, `kg`) — конвертируются в граммы и суммируются; при итоге `≥ 1000` выводятся в кг, иначе в г.
- **Объём** (`ml`, `l`) — конвертируются в миллилитры и суммируются; при итоге `≥ 1000` выводятся в литрах, иначе в мл.
- **Штуки** (`pcs`) — просто суммируются.
- **Бытовые меры** (`glass`, `tbsp`, `tsp`, `pinch`) — не конвертируются; разные бытовые меры не объединяются; одинаковая мера + то же имя суммируется сырыми числами.

Продукты с одинаковым нормализованным именем, но разными группами единиц (например `"мука"` 300 г в одном рецепте и `"мука"` 1 стакан в другом) — **отдельные строки**: весовая строка + строка бытовой меры, так как их нельзя корректно свести.

### Масштабирование и вывод

`scaledAmount = amount * (portions / рецепт.servings)` — `portions` всегда берётся из записи плана (`PlanEntry.Portions`), `servings` рецепта — делитель. Каждая запись плана вносит свой вклад: один и тот же рецепт в двух слотах масштабируется по своим порциям в каждом. Пустые слоты ничего не добавляют.

Округление не применяется: `amount` хранит сырое значение. Вывод `display` обрезает хвостовые нули (`2.50` → `2.5`), десятичный разделитель — точка (`"1.5 л"`); дробные количества показываются как есть (`0.5`, `1.5`). Для бесконечных десятичных дробей (например `1/3`) вывод ограничен 10 знаками после запятой. Русские формы бытовых мер склоняются (`1 ст. ложка`, `2 ч. ложки`, `5 стаканов`, дробные — `1.5 стакана`).
